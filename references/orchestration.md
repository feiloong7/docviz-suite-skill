# 编排与验收规则

## 统一事实模型

确认前建立一份内部事实清单，后续所有图共用，避免同一术语在不同图中含义漂移：

- `source_refs`：章节标题或原文定位；无法定位时标记待复核。
- `entities`：业务对象、角色、系统、模块、数据实体。
- `events`：触发动作、时间边界、前置条件、后置结果。
- `decisions`：判断条件、每个互斥分支、默认/缺失分支。
- `calculations`：公式、变量、单位、精度、日期和取数口径。
- `states`：状态、允许迁移、终态、异常回退。
- `interfaces`：调用方、被调方、协议/数据、同步异步；仅记录文档明确内容。
- `rules`：约束、红线、权限、校验、验收标准。
- `outputs`：指标、报表、状态、通知或其他结果。
- `gaps`：歧义、缺失、冲突、待用户确认项。

不要把事实清单扩展成另一套庞大交付物。它是保持各图一致的工作底稿。

## 产物职责与顺序

### 00_生成计划.md

确认前唯一正式文档产物。必须包含：一句话理解、文档类型及判断依据、范围、核心对象/流程、重要规则或架构关系、章节覆盖、缺口、产物清单和确认码。不要在此阶段提前生成“预览版”图表绕过确认门。

### 01_文档理解.html

面向第一次读文档的人。建议顺序：本质与目标 → 输入/处理/输出 → 主线或时间轴 → 分支/状态/依赖 → 核心规则 → 风险与待确认项。复杂分支的结果必须逐分支独立成行，不把多个结果塞在同一单元格。

### 02_总览信息图.html

面向快速回顾。只保留核心骨架和关键关系，不复制全量大纲。图形形态由内容关系决定；不要为凑模板添加文档没有的层次。

### 03 主图

一张图只回答一个主问题，保持一条明显主路径：

- 业务规则：端到端主流程，支路从最近主节点分出，公式放在关联节点或公式卡。
- PRD：核心用户旅程或功能状态；角色/权限用泳道或边界，交互调用可另选时序图。
- 系统文档：按内容选择架构、数据流、时序或生命周期，不把部署、调用链和业务流程强塞一张图。

Archify 新流程使用 workflow `schema_version: 2`。先自动布局；校验失败后按诊断修复，不为消除交叉而删除有业务含义的边。标准密度可用 `standard`，只有满足全部 showcase 检查时才声明 showcase 通过。

### 04_细节流程.html

只展开主图无法清楚表达的复杂部分。判断节点每条出口必须有条件标签；开始/结束明确；公式、异常和回退保持源文档语义。保留可编辑 Mermaid 源码，正式标准图遵守 GB 1526-89。

### 05 全量大纲与导图

大纲负责证明章节覆盖，导图负责分层浏览。不得只复刻目录而忽略关键规则；也不得为了美观删除细节。默认折叠到章节/小节节层，长文本提供悬停或详情查看；首屏文字应可读，不为整图适配而无限缩小。

### 06 关系图谱

节点与边必须来自事实清单。每条边使用有意义的关系名，并保留来源章节或 `source_file`。区分：

- `EXTRACTED`：文档直接陈述。
- `INFERRED`：推定关系，必须带置信度且默认不向用户冒充事实。
- `AMBIGUOUS`：歧义关系，进入待确认清单。

Graphify 自动语义抽取需要用户已有 API Key。没有 Key 时，可由助手抽取 graphify 原生 JSON，再用 graphify 导出和查询；明确标注“人工语义抽取 + graphify 原生渲染”。社区中文标签若未显示，检查 `.graphify_labels.json` 后重新导出。

### 00_可视化导航.html

最后生成。推荐入口通常为“理解页 → 总览 → 主图 → 细节 → 导图 → 图谱”。列出源文件、哈希、生成时间、文档 profile、实际产物和未解决缺口。所有相对链接必须真实存在，不链接计划中的未来文件。

## 上游调用约束

- 调用前读取当前安装版本的对应 `SKILL.md`；上游接口可能已变化，不能只依赖本编排文档。
- 保留上游技能自己的校验、交付和安全约束；本技能的计划确认不替代其质量检查。
- Windows 下给原生 Node 传 Windows 风格路径；Archify 设置 `ARCHIFY_UPDATE_CHECK_DISABLED=1`，避免其自身更新检查与 docviz-suite-skill 的确认流程重复。
- 不在上游技能目录写业务产物，不修改其源文件来实现某次文档生成。
- 输出使用用户语言，保留原文中的标识符、公式符号、接口名和产品名。

## 降级与依赖

- 缺少某个上游：标记对应产物未生成，继续不依赖它的部分；不得把其他工具的输出冒充该技能产物。
- Archify 不可用：可用内嵌 SVG 流程/架构图降级，但文件名和报告中标注“SVG 降级”。
- Graphify 不可用：可交付 `graph.json` 和关系表，但不得声称已生成 graphify 交互图。
- 文档内容不适合某产物：在计划中说明理由并请求确认删减，而不是机械生成空图。
- 多份源文档：先确认范围与主次关系，再建立统一事实模型；版本冲突必须显式列出。

## 覆盖与质量检查

### 语义覆盖

- 每个源章节至少被大纲覆盖；核心规则还应在理解页、主图或细节图之一出现。
- 每个判断的每个分支都有条件、结果和去向；分支结果逐行显示。
- 每个公式保留变量含义、单位、精度、日期边界及适用范围。
- 每个 PRD 功能可追溯到角色/场景和验收标准；文档没有验收标准时标为缺口。
- 每个系统外部依赖保留方向、用途和文档明确的协议；没有协议不得补写。

### 一致性

- 名称、编号、状态、公式在所有产物中一致。
- 主图与细节图不矛盾；图谱不引入文档外关系。
- 源文件改变后整批成果视为过期，必须重新确认。

### 呈现

- 浅色主题下使用浅底深字；深色主题下使用深底浅字。
- 首屏可理解，长文不溢出，节点不遮挡，连线不穿过无关节点。
- 对关键 HTML 做实际打开或截图检查；未执行时写“视觉检查未执行”，不能声称已检查。
- `verify` 通过只代表结构和链接检查通过，不替代人工语义复核。
